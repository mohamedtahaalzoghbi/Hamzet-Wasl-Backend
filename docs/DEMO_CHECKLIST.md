## 3. السيناريوهات الحية بالتفصيل

<div dir="rtl">

### السيناريو 1 — الإتاحة (دقيقتان)

</div>

1. `POST /api/v1/auth/login` بحساب `demo.disabled@hamzetwasl.local` وكلمة المرور `Demo@12345`.
2. `PUT /api/v1/me/accessibility` مع `needTypes: ["visual","hearing"]` ← 200، والاستجابة تُرجع
   `needType` و `needTypes` و `effectivePreset`.
3. نفس الطلب بأربع فئات ← **400** مع خطأ على الحقل `needTypes` (قاعدة التعدد).
4. `GET /api/v1/me/accessibility` ← نفس القيم محفوظة في قاعدة البيانات.

```json
{
  "needType": "visual",
  "needTypes": ["visual", "hearing"],
  "theme": "system",
  "fontScale": 1.0,
  "reducedMotion": false,
  "interactionMode": "touch",
  "notificationMode": "in_app"
}
```

<div dir="rtl">

### السيناريو 2 — المنظمة والأدمن (دقيقتان)

</div>

1. دخول بحساب `demo.company@hamzetwasl.local`.
2. `GET /api/v1/me/organization/review-status` ← يظهر `canSubmit` و `missingDocuments[]`.
3. `PUT /api/v1/me/organization/logo` ثم `PUT /api/v1/me/organization/documents/commercial_register`
   (طلب `multipart/form-data`).
4. `POST /api/v1/me/organization/submit` ← 200 مع `reviewId`، أو 422 إن نقص شيء (وهو مقصود للعرض).
5. دخول بحساب الأدمن ← `GET /api/v1/admin/organization-reviews` ثم
   `POST /api/v1/admin/organization-reviews/{id}/decision` ← يصبح الحساب `active` مع إشعار.
6. (اختياري) إظهار استقبال الإشعار لحظياً عبر SignalR.

<div dir="rtl">

### السيناريو 3 — المتطوع والمقابلة (دقيقتان)

</div>

1. دخول بحساب `demo.volunteer@hamzetwasl.local`.
2. `GET /api/v1/me/verification` ← `currentStep` و `steps[]` و `canBookInterview`.
3. `POST /api/v1/me/verification/evidence` بثلاثة ملفات ← 204.
4. `PUT /api/v1/me/verification/social-links` ← 204.
5. الأدمن ينشئ موعد مقابلة عبر `POST /api/v1/admin/interview-slots`، ثم المتطوع يحجز عبر
   `POST /api/v1/me/verification/interview` ← 200.

<div dir="rtl">

### سيناريو إضافي سريع (30 ثانية) — الأمان

</div>

- استخدام refresh token كـ Bearer ← **401** (لكل توكن غرض محدد).
- `POST /api/v1/auth/login` ببيانات خاطئة خمس مرات ← قفل الحساب.
- `PUT /api/v1/me/notifications/{id}/read` بمعرّف يخص مستخدماً آخر ← **404** (لا تسريب لوجود المورد).

## 5. نقاط القوة التقنية (استخدمها في الإجابة)

<div dir="rtl">

1. **مخطط واحد بلا ازدواجية**: سكربت SQL واحد مُضمَّن، مع اختبار تطابق (وحدة + تكامل) يفشل إن
   اختلّ التوازن بين نموذج EF Core والمخطط أو مع قيود CHECK.
2. **عقد واحد محكم**: غلاف موحّد، أكواد خطأ ثابتة، تواريخ UTC، ترقيم محدود، و`traceId` لكل رد.
3. **أمان مبني على المتطلبات**: توكنات بأغراض منفصلة، تدوير refresh، قفل الحساب، حد معدل لكل هوية،
   التحقق من ملكية المورد، التحقق من نوع الملف بالبصمة الثنائية، وعدم تسريب وجود المورد.
4. **إتاحة حقيقية**: حساب `effectivePreset` يدمج الفئات المتعددة وتفضيلات المستخدم، لا مجرد تخزين.
5. **كتالوج قابل للتطور**: المحافظات والمناطق في قاعدة البيانات مع cache وإمكانية التعطيل الإداري
   دون إعادة نشر.
6. **تغطية اختبار عالية**: 172 اختباراً (131 + 41) على قاعدة بيانات حقيقية، وكل إصلاح له اختبار رجعي.
7. **أتمتة كاملة**: خط CI يبني بتعامل التحذيرات كأخطاء، ويشغّل الاختبارين، ويفحص تطابق OpenAPI،
   ويفحص غياب الأسرار.
8. **توثيق محدَّث مع كل تغيير**: `CHANGELOG` و`DEVIATIONS` و`openapi.json` يُعاد تصديره آلياً.

</div>

## 6. أسئلة متوقعة من اللجنة وإجابات مختصرة

| السؤال | الإجابة المختصرة |
|---|---|
| لماذا لم تستخدم EF Core Migrations؟ | لأن المخطط المرجعي هو مصدر الحقيقة، والـ migrations كانت ستُنشئ مصدراً ثانياً قابلاً للتباعد. التطبيق يطبّق السكربت نفسه على أي قاعدة فارغة، واختبار التكامل يتحقق من الجداول وقيود CHECK. |
| كيف ضمنتم أن الواجهة الأمامية لن تنكسر؟ | `openapi.json` مُصدَّر من الـ API ويُعاد فحصه في كل تشغيل للخط CI، وأي تغيير في العقد يُسجَّل في `CHANGELOG.md`. |
| ماذا لو أُلغي حساب؟ | الطلب لا يحذف فوراً: `DELETION_REQUEST` يمر بموافقة الأدمن ثم تُخفى البيانات (anonymisation)، ويبقى سجل التدقيق. |
| كيف تتعاملون مع الملفات الحساسة؟ | تُخزَّن خارج الـ web root، وتُقدَّم عبر رابط موقّع صالح 10 دقائق، وتُفحص بصمة الملف الثنائية قبل الحفظ. |
| ما الفرق بين الأدمن والمتطوع في الصلاحيات؟ | سياسات `RequireRole` على مستوى الـ Controller: كل مجموعة مسارات محجوبة بدور، وأي محاولة خاطئة ترجع 403. |
| هل الاختبارات حقيقية أم ساذجة؟ | اختبارات التكامل تشغّل الـ API فعلياً على SQL Server حقيقي (تسجيل، رفع، مراجعة، إشعارات)، وتنشئ وتحذف قاعدة بيانات مؤقتة في كل تشغيل. |
| ما الذي يأتي بعد المرحلة الأولى؟ | المرحلة الأولى مكتملة ومختبَرة، والمؤجلات موثّقة (عمود `payload_json`، إدارة الكتالوج الجغرافي، وعمود `updated_at` للمراجعات). |
| ماذا لو تغيّر المخطط مستقبلاً؟ | يُعدَّل `Hamzet_Wasl_Schema_v2.sql` مع سكربت migration للـ bases الموجودة، وبموافقة مسبقة وتسجيل في `CHANGELOG` و`DEVIATIONS`. |

</div>
